RAG Evaluation: Measure Retrieval Before Blaming the LLM

A useful RAG scorecard separates what the system found from what the model wrote. Otherwise, every failure looks like a model failure.

A retrieval-augmented generation system gives an incorrect answer. The instinctive response is often to change the prompt or replace the language model. But the model may never have received the evidence required to answer correctly.

RAG contains at least two systems with different failure modes: a retriever selects context, then a generator produces an answer from it. Evaluating only the final response hides this boundary. A reliable evaluation process measures retrieval first, generation second, and the complete experience last.

Start with a test set, not a favorite demo

Build a small evaluation set from realistic information needs. Each case should contain the query, the documents or chunks considered relevant, and the expected answer behavior. Include straightforward questions, paraphrases, ambiguous requests, multi-document questions, and queries that should not be answered.

Negative cases matter because a system must recognize when its corpus lacks sufficient evidence. Microsoft’s RAG retrieval guidance recommends both positive examples, where relevant chunks should rank highly, and negative examples, where retrieval scores should remain low. Add access-control cases as well: a technically relevant document is still wrong context when the requester is not allowed to see it.

Keep the test set versioned beside the configuration that produced the result. Record the chunking strategy, embedding model, index version, filters, reranker, prompt, and generation model. Without that lineage, a score change is difficult to explain.

Measure whether retrieval supplied usable evidence

Three ranking metrics provide a practical starting point:

  • Precision@K asks what fraction of the first K retrieved items are relevant. Low precision means the context window is being filled with noise.
  • Recall@K asks what fraction of all known relevant items appears in the first K results. Low recall means important evidence is missing.
  • Mean Reciprocal Rank rewards placing the first relevant item near the top. It is useful when one strong result is sufficient for a query.

These metrics answer different questions. Increasing K can improve recall while reducing precision and consuming more context. A reranker may improve early ordering without recovering a document that the first-stage search never found. Report several metrics rather than collapsing retrieval quality into one number.

A runnable retrieval check

The following Python 3 example is deliberately provider-independent. It evaluates one synthetic query using document identifiers, so it can be run locally without an API key or external package.

from math import isclose

def precision_at_k(retrieved, relevant, k):
    top = retrieved[:k]
    return sum(doc in relevant for doc in top) / k

def recall_at_k(retrieved, relevant, k):
    if not relevant:
        return 1.0 if not retrieved[:k] else 0.0
    hits = sum(doc in relevant for doc in retrieved[:k])
    return hits / len(relevant)

def reciprocal_rank(retrieved, relevant):
    for rank, doc in enumerate(retrieved, start=1):
        if doc in relevant:
            return 1 / rank
    return 0.0

retrieved = ["doc-b", "doc-a", "doc-x"]
relevant = {"doc-a", "doc-c"}

assert isclose(precision_at_k(retrieved, relevant, 3), 1 / 3)
assert isclose(recall_at_k(retrieved, relevant, 3), 1 / 2)
assert isclose(reciprocal_rank(retrieved, relevant), 1 / 2)
print("Retrieval checks passed")

Save it as retrieval_eval.py and run python3 retrieval_eval.py. The first relevant item is second, only one of the top three results is relevant, and one of two relevant documents was recovered. To evaluate a suite, calculate each metric per query and average it across a fixed dataset. Preserve the per-case results: averages alone can hide a broken query category.

Evaluate generation with the retrieved context fixed

Once retrieval is acceptable, test the generator using a frozen set of contexts. This prevents index changes from confusing the diagnosis. Check whether claims are supported by the supplied context, whether the answer covers the necessary facts, whether citations point to the evidence they claim to support, and whether the model abstains when evidence is insufficient.

Microsoft’s RAG evaluator documentation makes the same architectural distinction: retrieval and document processing are evaluated separately from system-level properties such as groundedness and response completeness. Ragas also documents context precision as a way to assess whether relevant chunks are ranked ahead of irrelevant ones.

Automated scoring helps with regression testing, but it should not be the only judge. Sample failures for human review, especially in high-impact or specialized domains. Exact wording is not the goal; support, completeness, and safe behavior are.

Turn failures into engineering actions

A separated scorecard shortens the path from symptom to fix:

  • Low recall suggests inspecting parsing, chunk boundaries, query rewriting, indexing, metadata filters, or hybrid search.
  • Low precision with adequate recall suggests tuning ranking, reranking, filters, or the number of chunks passed forward.
  • Strong retrieval with unsupported claims points toward prompt design, context handling, or generation behavior.
  • Answers to negative cases expose an abstention or policy failure, even when the prose sounds convincing.

Run the suite whenever documents, parsers, embeddings, ranking logic, prompts, or models change. Treat it like the quality gate described in reliable CI testing: a regression check is useful only when its failures are reproducible and visible. Feed the results into the shared engineering loop discussed in development, DevOps, and QA feedback.

Evaluate the pipeline, not the brand name

RAG quality is not a property of the language model alone. It emerges from document preparation, retrieval, ranking, context assembly, generation, and policy decisions. Changing the model can improve fluency while leaving missing evidence untouched.

The practical rule is simple: first prove that the right information reached the model. Then prove that the model used it faithfully. Finally, test the system end to end with realistic and no-answer cases. That decomposition turns “the AI gave a bad answer” into a diagnosis an engineering team can act on.
