Hybrid Search for RAG: Fuse Keyword and Vector Results with RRF

Keyword retrieval understands exact identifiers. Vector retrieval captures semantic similarity. Reciprocal Rank Fusion combines their ranked lists without pretending their scores share the same scale.

A retrieval-augmented generation system can fail before the language model sees a prompt. If retrieval misses the relevant passage, a well-instructed model cannot cite information it never received. Relying on one retrieval method makes that failure more likely when the query distribution is mixed.

Keyword search is strong when wording matters: product codes, error messages, names, acronyms and exact phrases. Vector search is useful when the user’s language differs from the document’s language but the meaning is close. Hybrid search runs both and merges their results into one candidate list.

Why raw scores should not be added

Keyword and vector retrievers produce scores with different meanings and ranges. A BM25 score of 12 and a cosine similarity of 0.84 are not comparable measurements. Adding them directly makes the result depend on arbitrary scale rather than ranking quality. Score normalization can work, but its calibration becomes another model that must be monitored.

Reciprocal Rank Fusion, introduced by Cormack, Clarke and Büttcher in their 2009 SIGIR paper, avoids that scale problem. For each document, RRF adds 1 / (k + rank) from every ranked list in which it appears. A document near the top of multiple lists accumulates evidence; a document returned by only one method can still compete if it ranks highly.

Use RRF as a baseline, not a guarantee

Elastic’s current hybrid-search documentation recommends RRF for combining full-text and vector retrieval. Azure AI Search also executes text and vector queries in parallel and merges them with RRF, as described in its hybrid-search overview. These implementations make RRF a practical baseline, but no fusion rule guarantees better results for every corpus.

RRF discards score magnitude. The first and second documents in a list are treated according to position even if their original scores are nearly equal or dramatically different. If those margins carry useful information, a normalized score-based method may perform better. The correct choice is empirical: compare on labeled queries from the intended workload.

A runnable RRF implementation

The following Python example fuses two ranked lists. In a real system, the lists would come from a lexical retriever and a vector index. The code uses stable document identifiers so the same document can be recognized across both channels.

from collections import defaultdict

def reciprocal_rank_fusion(rankings, k=60):
    scores = defaultdict(float)
    evidence = defaultdict(list)

    for source, documents in rankings.items():
        for rank, document_id in enumerate(documents, start=1):
            scores[document_id] += 1.0 / (k + rank)
            evidence[document_id].append((source, rank))

    ordered = sorted(
        scores,
        key=lambda document_id: (-scores[document_id], document_id),
    )
    return [
        {
            "document_id": document_id,
            "rrf_score": round(scores[document_id], 6),
            "evidence": evidence[document_id],
        }
        for document_id in ordered
    ]

rankings = {
    "keyword": ["doc_error_503", "doc_retry", "doc_timeout"],
    "vector": ["doc_timeout", "doc_error_503", "doc_backoff"],
}

for result in reciprocal_rank_fusion(rankings):
    print(result)

The shared documents rise because both retrievers support them. The deterministic document-ID tie-breaker keeps test output stable. Keep the source ranks in telemetry; a final fused score without its evidence is difficult to debug.

Candidate depth changes the result

Fusion can only rank documents that a child retriever returns. If each channel supplies five candidates, a relevant document ranked sixth by both is invisible. Retrieve a wider pool than the final context size, fuse it, apply permission and metadata filters, then optionally rerank the smaller set before selecting chunks for the prompt.

Do not confuse the RRF rank constant with vector k, the number of nearest neighbors. The rank constant controls how quickly contribution falls with position; candidate depth controls which documents can participate. Tune them separately. Azure’s RRF scoring guide documents the formula and uses 60 as its rank constant. Treat that value as a starting point, not a universal optimum.

Evaluate retrieval before generation

Create a query set that deliberately mixes exact identifiers, paraphrases, ambiguous short queries and terminology mismatches. For each query, label relevant documents and compare keyword-only, vector-only and hybrid runs using recall at candidate depth, mean reciprocal rank and nDCG. Slice results by query type; one aggregate score can hide that hybrid retrieval helps paraphrases while harming exact-code lookup.

The earlier guide on measuring retrieval before the LLM provides the evaluation structure. When comparing two configurations on the same queries, apply the paired-case approach from LLM evaluation with uncertainty.

A robust RAG pipeline does not choose keyword or vector retrieval as a matter of fashion. It preserves the strengths of both, fuses their evidence transparently and measures the combined ranking on real query classes. RRF is valuable because it is simple, inspectable and indifferent to incompatible score scales. Its simplicity is a baseline for disciplined experiments, not a substitute for them.
