The Model Is Not the System: Harness Engineering for Reliable AI Agents

An agent that survives a demo is useful. An agent that survives a crash, resumes correctly, and proves its work is engineering.

An AI coding agent edits a repository, runs a command, and announces success. Then its process dies before the result is checked. When the worker restarts, should it repeat the edit, trust the previous message, or inspect what actually happened?

A larger context window does not answer that question. Neither does a more persuasive prompt. It is a systems problem: work has state, actions have consequences, and completion requires evidence.

Harness engineering is the work of building the runtime around a model: the machinery that selects context, executes tools, records progress, handles interruption, and checks results. For developers building agent products, that machinery deserves the same attention as model selection.

Why this belongs in the 2026 engineering conversation

Recent primary sources make the shift concrete. Anthropic’s April 2026 architecture report describes separating session storage, the harness, and execution sandboxes so components can fail independently. Its March 2026 application-development report describes explicit sprint contracts and an evaluator exercising applications.

A May 2026 research preprint similarly frames software-engineering capability as a property of the model, harness, and environment together. This is a proposed research framework, rather than an industry standard or proof that one architecture wins everywhere.

My engineering interpretation is straightforward: as agents move from answering questions to changing systems, the unit of design becomes the complete execution path. The model proposes work; the surrounding software determines whether that work can be performed, recovered, and accepted.

A transcript is not a task database

Conversation history explains what an agent saw. Operational state explains what the application knows. Mixing them makes recovery fragile: a sentence saying “tests passed” is not equivalent to a stored result tied to the exact artifact under review.

For a fictional documentation agent, record a task identifier, input revision, output location, current stage, and verification evidence. Keep the generated document separate from the status that says it is accepted. A worker restart should reload those records rather than reconstruct truth from conversational confidence.

The same principle applies to coding: a check must identify the commit or artifact it examined. A passing test from yesterday cannot validate a file edited today. State should express that dependency explicitly.

Define transitions before adding more intelligence

A small lifecycle can distinguish pending work, generated output, verified output, and failure. These states answer different questions. Generated means an artifact exists. Verified means specified checks passed. Published means a separate delivery action was confirmed.

Require evidence for each consequential transition. An agent may request publication, but application code should check the artifact revision and authorization first. Failed or interrupted work should remain visible as failed or interrupted; a fluent final message must not quietly promote it to completed.

This extends the architecture choice in AI agents versus workflows: whichever controls the next step, the surrounding system still owns task state.

A runnable checkpoint and recovery example

This Python 3 example uses SQLite and a synthetic model output. It demonstrates recovery after process interruption, with generated output committed before verification. It calls no LLM and performs no external action.

import json
import sqlite3
import sys

with sqlite3.connect("harness-demo.db") as db:
    db.execute("""CREATE TABLE IF NOT EXISTS jobs (
        id TEXT PRIMARY KEY, stage TEXT NOT NULL,
        artifact TEXT, evidence TEXT
    )""")
    db.execute("INSERT OR IGNORE INTO jobs VALUES (?, ?, ?, ?)",
               ("demo-v1", "pending", None, None))

with sqlite3.connect("harness-demo.db") as db:
    stage, artifact = db.execute(
        "SELECT stage, artifact FROM jobs WHERE id=?",
        ("demo-v1",)).fetchone()
    if stage == "pending":
        # Synthetic stand-in for a model-produced artifact.
        artifact = json.dumps({"total": 6})
        db.execute("UPDATE jobs SET stage=?, artifact=? WHERE id=?",
                   ("generated", artifact, "demo-v1"))

# The artifact is committed before the simulated interruption.
if "--crash" in sys.argv:
    raise SystemExit("Interrupted before verification; rerun normally")

with sqlite3.connect("harness-demo.db") as db:
    stage, artifact = db.execute(
        "SELECT stage, artifact FROM jobs WHERE id=?",
        ("demo-v1",)).fetchone()
    if stage == "generated":
        expected = sum([1, 2, 3])  # Independent fixture oracle.
        passed = json.loads(artifact).get("total") == expected
        evidence = json.dumps({"check": "fixture_sum", "passed": passed})
        db.execute("UPDATE jobs SET stage=?, evidence=? WHERE id=?",
                   ("done" if passed else "failed", evidence, "demo-v1"))
    print(db.execute("SELECT stage, evidence FROM jobs WHERE id=?",
                     ("demo-v1",)).fetchone())

Save it as harness_demo.py in an empty directory. Run python3 harness_demo.py --crash, then python3 harness_demo.py. The second invocation loads the saved artifact and prints a done record with passing evidence. Run it again: the completed task is read rather than generated again. Delete harness-demo.db to reset this disposable exercise.

The verifier computes its expected value from a fixture instead of asking the simulated generator whether it is correct. The example’s transaction boundaries follow Python’s SQLite connection semantics: successful transaction blocks commit, while exceptions roll back pending changes.

This is deliberately a single-worker demonstration of process recovery. It is not a distributed scheduler, a power-loss durability test, or an exactly-once guarantee for remote effects. Multiple workers require coordination; external writes require their own recovery contract.

The difficult boundary is outside your database

Suppose an agent publishes a report successfully, but the network drops before the service returns a response. Its local record may still say “generated.” Blindly repeating publication can create a duplicate.

Use a stable operation identity supported by the destination, or reconcile the destination’s state before retrying. Keep uncertain outcomes distinct from known failures. A local transaction cannot atomically commit an unrelated remote service’s work. The underlying issue is the same one discussed in idempotency and duplicate effects.

Sandbox isolation matters for a different reason. Generated code should run with only the capabilities it needs. Keep durable control records and privileged credentials behind interfaces the execution environment cannot casually overwrite or read. Anthropic’s managed-agent report provides one concrete example of separating these concerns; the appropriate implementation depends on your deployment.

Measure recovery, not just the happy path

Build an evaluation set around interruptions and observable outcomes. Terminate a worker after generation. Return a timeout after a simulated remote success. Feed the verifier a wrong artifact. Change the input revision after a previous check passed. Exhaust the tool budget before completion.

For each case, specify what must remain true: no duplicate external effect, no stale acceptance, no lost artifact, and an honest final status. Record the action trace as well as the final answer. Anthropic’s agent-evaluation guidance distinguishes task outcomes from execution traces and explains why both matter.

Track verified completion rate, recovery success, duplicate-effect rate, elapsed time, and cost per accepted task. Compare changes using the same cases and repeat stochastic runs. Improvements in one metric can hide regressions in another.

Build the smallest runtime you can explain

Begin with one worker, explicit stages, stored artifacts, and an independent check. Add queues, leases, richer memory, or additional agents only when a measured failure requires them. Revisit model-specific workarounds after model upgrades; the March and April reports both illustrate assumptions becoming unnecessary as model behavior changes.

The commercial value is a system whose behavior remains inspectable after the demo ends: you can explain what happened, recover unfinished work, and connect acceptance to evidence. A capable model makes ambitious work possible. A well-designed harness makes its execution accountable.
