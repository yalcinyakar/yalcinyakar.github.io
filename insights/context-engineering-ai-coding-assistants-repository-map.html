Context Engineering for AI Coding Assistants: Build a Repository Map, Not a Code Dump

Giving a coding assistant more files is not the same as giving it better context. A small, task-specific repository map can be easier to inspect, safer to share and more useful to the model.

When an AI coding assistant produces a change that ignores a local convention, edits the wrong layer or invents a test command, the first instinct is often to improve the prompt. The real problem may be the context assembled around that prompt.

A request such as “add retry handling” is incomplete without the relevant interface, the caller, error policy, nearby tests and the repository’s validation commands. At the other extreme, attaching the entire repository introduces unrelated code, generated files and potentially sensitive material. Context engineering is the discipline of selecting the smallest useful evidence set for the task.

Start with a task map

Before asking the model to change code, translate the request into a compact map. Identify the target file, its direct dependencies, the tests that observe the behavior, and the commands that define success. Include architecture notes or interface contracts only when they constrain the change.

Anthropic’s context engineering guidance describes context as a finite resource and recommends the smallest set of high-signal tokens that fully communicates expected behavior. That principle applies directly to coding work: relevance should determine inclusion, not repository size.

A useful task map can answer five questions:

  • What behavior must change, and what must remain stable?
  • Which file owns that behavior?
  • Which interfaces and callers constrain the implementation?
  • Which tests or checks provide an independent oracle?
  • Which files are prohibited from entering model context?

Separate durable instructions from task evidence

Repository-wide rules should not be repeated in every request. Put stable information—build commands, test commands, directory roles, coding conventions and safety boundaries—in the instruction mechanism supported by the tool. GitHub’s documentation for repository custom instructions explicitly positions them as project-specific context for frameworks, architecture, coding and testing conventions. It also supports path-specific instructions so guidance for one area does not overload every task.

Task evidence is different. It changes with every issue: the current diff, the exact interface, a failing test, or a short design decision. Keep these two layers distinct. Durable instructions explain how the repository works; task evidence explains what is happening now.

Instructions are guidance, not enforcement. Build, lint, type, security and test checks must still run outside the model. For generated tests, use independent test oracles instead of allowing the assistant’s implementation and expectations to validate each other.

Apply a context budget and a denylist

A context builder should be deterministic enough to review. Rank candidate files by relationship to the task, reject sensitive paths before reading their contents, and stop when the explicit budget is exhausted. The budget may be tokens in a real integration; the character limit below keeps the example dependency-free.

from dataclasses import dataclass
import re

@dataclass(frozen=True)
class Candidate:
    path: str
    relation: str
    content: str

PRIORITY = {"changed": 0, "dependency": 1, "test": 2, "docs": 3}
DENIED = [r"(^|/)\.env($|\.)", r"\.(pem|key)$", r"(^|/)secrets?/"]

def is_denied(path):
    return any(re.search(pattern, path, re.I) for pattern in DENIED)

def build_context(candidates, budget=520):
    blocks, manifest, used = [], [], 0
    for item in sorted(candidates, key=lambda x: (PRIORITY[x.relation], x.path)):
        if is_denied(item.path):
            continue
        block = f"## {item.path} [{item.relation}]\n{item.content.strip()}\n"
        if used + len(block) > budget:
            continue
        blocks.append(block)
        manifest.append(item.path)
        used += len(block)
    return "\n".join(blocks), manifest

candidates = [
    Candidate("app/service.py", "changed", "from app.pricing import total\n\ndef quote(items): return total(items)"),
    Candidate("app/pricing.py", "dependency", "def total(items): return sum(items)"),
    Candidate("tests/test_service.py", "test", "def test_quote(): assert quote([2, 3]) == 5"),
    Candidate("docs/architecture.md", "docs", "service.py owns quote orchestration"),
    Candidate(".env", "dependency", "API_TOKEN=never-share-this"),
]

bundle, manifest = build_context(candidates)
print("selected:", manifest)
print(bundle)
assert manifest[0] == "app/service.py"
assert ".env" not in manifest and "never-share-this" not in bundle
assert len(bundle) <= 520

Save the example as context_map.py and run python3 context_map.py. It selects the changed file first, then related implementation and tests while excluding .env. A production version should derive relationships from a language-aware dependency graph, test metadata and the actual diff rather than accepting manually labelled candidates.

Path filtering is only one control. Secrets can exist in ordinary source, logs or fixtures, so scan content before sending it to a model and minimize retention. Treat retrieved repository text as untrusted data as well. OWASP’s context-window security guidance notes that confidential content and untrusted instructions can coexist in the same model input, creating exposure and prompt-injection risks.

Make the bundle observable

Record the manifest, selection reason, budget, excluded paths and source revision alongside each AI-assisted change. This makes context failures diagnosable: reviewers can see whether the assistant missed a contract because it was absent, ignored it despite being present, or received contradictory instructions.

After generation, verify the patch against the original task map. Run deterministic checks, inspect the diff, and reject unrelated edits. Validate any structured model output before it reaches automation, following the layered approach in LLM output validation beyond valid JSON. If an assistant can call tools or modify external state, use the execution limits and recovery controls described in harness engineering for reliable AI agents.

Good context engineering does not try to make the model know everything. It gives the model the evidence required for one bounded decision, preserves a record of that evidence, and leaves acceptance to independent engineering controls.
