Flaky Tests in CI: How to Restore Trust Without Hiding Failures

A flaky test does more than waste pipeline time. It teaches teams to distrust failures. The solution is not a permanently green build, but a delivery system where red still means something.

A test that fails consistently is useful. It tells the team that something is broken. A test that sometimes passes and sometimes fails under the same conditions is more dangerous. It creates uncertainty: is the product defective, is the environment unstable, or is the test itself unreliable?

These non-deterministic tests—commonly called flaky tests—do more than slow down a CI pipeline. They gradually train developers to distrust automation. Once “just rerun it” becomes the default response, a genuine regression can be dismissed as another false alarm.

The goal is therefore not simply to make the pipeline green. It is to restore the relationship between a failed test and a real engineering problem.

What is a flaky test?

A flaky test produces different results without a relevant change to the application or test code. The same commit may pass in one pipeline run and fail in the next.

The official pytest documentation describes flakiness as intermittent or apparently non-deterministic failure. Flakiness is usually caused by an uncontrolled dependency rather than true randomness. Somewhere in the execution path, the test depends on state, timing, ordering, infrastructure, or data it does not fully control.

A trusted pipeline is not one that always appears green. It is one where a failure remains a useful engineering signal.

Classify the failure before fixing it

Treating every flaky test as a synchronization problem leads to unnecessary waits and slower pipelines. Start by placing the failure into a practical category.

1. Shared state

Tests may reuse database records, files, browser sessions, caches, message queues, or global variables. One test changes the environment and another unknowingly inherits the result. This type of failure often appears when tests run in parallel or in a different order.

Each test should create the state it needs and uniquely isolate or remove that state afterward. Selenium’s guidance recommends avoiding shared test data and creating a separate WebDriver instance for each test. See Avoid sharing state.

2. Timing and asynchronous behavior

Fixed delays such as sleep(5) assume the system will reach the expected state within an arbitrary period. The delay may be unnecessarily long on a healthy run and still too short when the environment is busy.

Replace fixed sleeps with bounded condition-based waits. Wait for a meaningful event: an element becomes interactable, a record reaches the expected status, a response satisfies a defined condition, or a background operation reports completion. Every wait should still have a finite timeout; an unlimited wait converts a flaky failure into a hanging pipeline.

3. Test-order dependency

A test that passes only after another test is not independent. It is an undocumented workflow split across multiple test cases. Run suspicious tests individually, in randomized order, and in parallel. If the result changes, inspect setup and teardown logic, reused identifiers, global configuration, and data that survives between cases.

The fix is normally to move required preparation into an explicit fixture or setup step—not to enforce a permanent execution order.

4. External dependencies

Third-party APIs, shared environments, DNS, network latency, rate limits, and temporary service outages can make a deterministic test appear unstable. Decide what the test is supposed to prove. If it verifies internal behavior, replace the external dependency with a controlled stub or contract test. If it intentionally verifies the real integration, classify it accordingly and apply an appropriate execution policy.

Not every test belongs in the pull-request quality gate.

5. Overly strict assertions

A correct result can still fail because of insignificant differences in timestamps, floating-point calculations, generated identifiers, ordering, or eventually consistent data. Assertions should be precise about business behavior but tolerant of irrelevant variation. The answer is not weaker validation; it is validation aligned with the actual contract.

Capture evidence on the first failure

A rerun can remove the only visible trace of the problem. Before retrying, preserve enough evidence to reconstruct the original execution.

For UI tests, capture the screenshot, browser console output, current URL, relevant network failures, element locator, wait condition, and browser and driver versions. For API and integration tests, capture sanitized request and response metadata, the correlation identifier, response status and duration, dependency health, test-data identifier, and relevant service logs.

For every test, record the commit, execution node, attempt number, start time, duration, random seed, and parallel worker. Sensitive information must be masked. Diagnostic value does not require exposing credentials, personal data, or complete production-like payloads.

Use retries as a diagnostic tool, not a cure

A limited automatic rerun can keep delivery moving while evidence is collected. However, a passing retry does not convert the first failure into success. Report outcomes separately: passed on the first attempt, failed then passed on retry, failed on every attempt, or executed in quarantine.

Retries should be bounded and selective. Repeating the entire suite wastes resources and makes unrelated results harder to interpret. Retry only the failed test when isolation is guaranteed, preserve every attempt, and maintain a counter showing how often retries are needed. An increasing retry-pass rate is an early warning that test reliability is deteriorating.

Quarantine must have an expiration date

Quarantine can temporarily remove a known flaky test from the blocking quality gate. It should not become a permanent archive for inconvenient failures.

  • Assign an owner and document the reason.
  • Link a defect or engineering task.
  • Record the quarantine date and a review deadline.
  • Continue running the test in a non-blocking stage.

A quarantined test that is no longer executed provides no information. A quarantined test without an owner is effectively deleted, but with extra ceremony. If the behavior is already covered reliably at another level, deletion may be correct. Otherwise, repair or redesign it.

Measure reliability as an engineering metric

Counting flaky tests is not enough. Track first-attempt pass rate, retry-pass rate, flaky failures per 1,000 executions, median time in quarantine, root-cause category, pipeline time consumed by reruns, and repeated failures over a rolling period.

Measure at test level rather than only pipeline level. A suite with a 95% pass rate may contain one severely unstable test or hundreds of mildly unstable ones. Those situations require different responses.

A sustainable flaky-test workflow

  1. Preserve evidence from the first failure.
  2. Rerun the failed test under controlled conditions.
  3. Classify the likely cause.
  4. Quarantine only when necessary.
  5. Assign an owner and deadline.
  6. Repair, replace, lower, or delete the test.
  7. Run it repeatedly and in parallel before restoring it.
  8. Monitor whether the same failure pattern returns.

For browser automation, starting each test from a fresh browser profile is one of the strongest isolation boundaries. Selenium recommends a fresh browser per test when fully disposable environments are impractical.

Conclusion

Flaky tests are not harmless noise. They are defects in the delivery system. Reruns can reduce short-term disruption, and quarantine can protect the quality gate temporarily. Neither should hide the original failure.

The durable solution is to control state, replace arbitrary delays, isolate dependencies, capture evidence, and make test reliability measurable. This is part of building a shared engineering feedback loop in which development, DevOps, and QA work from the same trustworthy signals.
