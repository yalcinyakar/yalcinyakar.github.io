AI-Generated Code Review: Build a Diff Risk Map Before You Merge

An AI explanation can sound confident while a patch quietly changes dependencies, authorization, migrations or tests. Review the evidence in the diff first.

AI coding assistants can produce a plausible implementation and a polished summary in the same response. The summary is useful orientation, but it is not independent evidence. The patch, its execution results, and the repository’s acceptance rules are what should determine whether a change is safe to merge.

A practical review begins by turning the diff into a risk map. The map does not judge correctness. It identifies which surfaces changed, which evidence is required, and where a reviewer should spend attention. This keeps review proportional: a copy change and an authentication change should not receive the same checklist.

Start with changed behavior, not generated prose

Read the request and acceptance criteria before the implementation. Then inspect the changed files and ask four questions: What behavior was added or removed? Which trust boundary moved? Which persistent data or external interface changed? Which automated checks demonstrate the intended result?

GitHub’s guidance for reviewing AI-generated code recommends compiling and testing first, checking alignment with repository intent, scrutinizing dependencies, and watching for deleted or skipped tests. Its responsible-use guidance for agents also treats generated code and commands as material that must be reviewed and verified before merge or execution.

The same discipline applies regardless of which model produced the patch. Do not ask the generator whether its own work is correct and treat the answer as validation. Use repository-controlled tests, static analysis, schema checks, dependency policy, and human review of domain decisions.

Classify the diff into review surfaces

Begin with filenames because they provide a cheap, deterministic routing signal. A useful first pass can classify:

  • Dependencies: manifests and lockfiles require package identity, version, license, maintenance and vulnerability checks.
  • Security boundaries: authentication, authorization, secrets, cryptography and request validation require focused threat review.
  • Persistence: migrations and schema changes require compatibility, rollback and data-loss analysis.
  • Delivery: workflow, container and infrastructure files can change permissions or deployment behavior.
  • Tests: removed assertions, new skips or fixtures that mirror implementation assumptions deserve explicit review.

NIST’s Secure Software Development Framework places code review and analysis inside the development workflow, with issues recorded and triaged rather than treated as an informal final glance. A risk map is a routing layer for those controls, not a substitute for them.

A runnable diff risk mapper

The following Python 3 script reads the output of git diff --numstat. It totals the changed lines and assigns review tags from explicit path rules. Binary changes are handled without pretending their contents were inspected.

import sys
from pathlib import PurePosixPath

RULES = {
    "dependencies": {"package.json", "package-lock.json", "poetry.lock"},
    "security": {"auth", "permission", "secret", "crypto"},
    "persistence": {"migration", "schema"},
    "delivery": {".github/workflows", "dockerfile", "terraform"},
    "tests": {"test", "spec"},
}

def classify(path):
    normalized = str(PurePosixPath(path)).lower()
    return [
        tag for tag, needles in RULES.items()
        if any(needle in normalized for needle in needles)
    ]

def parse_numstat(lines):
    records = []
    for line in lines:
        added, deleted, path = line.rstrip("\n").split("\t", 2)
        binary = added == "-" or deleted == "-"
        records.append({
            "path": path,
            "added": 0 if binary else int(added),
            "deleted": 0 if binary else int(deleted),
            "binary": binary,
            "tags": classify(path),
        })
    return records

sample = [
    "8\t2\tsrc/auth/session.py\n",
    "1\t1\tpackage-lock.json\n",
    "12\t0\ttests/test_session.py\n",
]
input_lines = list(sys.stdin)
records = parse_numstat(input_lines or sample)

for item in records:
    tags = ",".join(item["tags"]) or "general"
    size = "binary" if item["binary"] else f"+{item['added']}/-{item['deleted']}"
    print(f"{size:10} {tags:24} {item['path']}")

assert {tag for item in records for tag in item["tags"]} >= {
    "security", "dependencies", "tests"
}

Save it as diff_risk_map.py. Run the built-in example with python3 diff_risk_map.py, or analyze a repository with git diff --numstat origin/main...HEAD | python3 diff_risk_map.py. The rules are intentionally transparent. Extend them with the paths and evidence requirements that match your architecture.

Convert tags into required evidence

A tag should trigger a concrete review action. A dependency change needs a lockfile diff and verified package source. A migration needs forward and rollback tests against representative schema states. An authorization change needs negative tests proving forbidden actions remain forbidden. A workflow change needs permission review and a test in a non-production environment.

For built artifacts, the SLSA provenance specification defines verifiable information about where, when and how an artifact was produced, including resolved dependencies when known. Provenance helps connect a reviewed source revision to an artifact; it does not prove the source logic is correct.

Require tests that can fail for the right reason. The article on independent oracles for AI-generated tests explains why assertions copied from the implementation provide weak evidence. For large tasks, first give the assistant a scoped repository map so it changes fewer unrelated surfaces. If an agent can execute tools, validate its tool contracts before actions run.

Keep the merge decision human-readable

The final review note should be short and auditable: intended behavior, risk tags, tests executed, unresolved findings, dependency or migration decisions, and the reviewer responsible for acceptance. Preserve command output in CI rather than pasting unverified claims from the generator.

AI can accelerate implementation and review preparation. It should not collapse authorship, evidence and approval into one opaque step. Build the risk map from the diff, route each surface to the right checks, and merge only when independent evidence supports the change.
