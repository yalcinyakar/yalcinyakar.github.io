AI Agent Tool Contracts: Validate Before You Execute

A reliable agent tool is more than a function the model can call. It is a controlled boundary that validates intent, applies policy and makes side effects observable before execution.

AI agents become operationally useful when they can call tools: search a catalogue, update a record, create a ticket or trigger a workflow. That same capability creates the main engineering risk. A model can propose an action, but the application still owns the consequences. The tool boundary must therefore reject malformed arguments, enforce authorization and separate a proposed action from an executed one.

Think of each tool as a small public API. Its contract should answer five questions: what arguments are accepted, who may call it, what resources it may affect, whether it changes state and how a repeated request behaves. A persuasive model explanation is not part of that contract.

Start with a narrow schema

OpenAI’s function-calling guide defines tool parameters with JSON Schema and recommends strict mode. Strict schemas improve structural reliability, but they do not express every business rule. A field can be a valid string and still contain an unauthorized account identifier. A quantity can be a valid integer and still exceed the caller’s limit.

Use enums instead of open text where the domain is finite. Reject unknown properties. Add length and range limits. Keep identifiers distinct instead of accepting one generic target field. Then validate the parsed call again in application code. Schema validation establishes shape; policy validation establishes permission.

Classify the side effect

Not all tools deserve the same execution path. A read-only lookup can often run immediately after authorization. A reversible update may require a preview. A destructive or externally visible action should pause for approval. OpenAI’s guardrails and human review guide places checks next to the function tool and recommends approval interruptions for sensitive side effects.

The Model Context Protocol uses annotations such as read-only, destructive and idempotent as risk vocabulary. Its tool-annotations guidance also warns that annotations are hints, not security controls. Treat them as metadata for routing and user interfaces; enforce the rule in trusted code.

Keep discovery separate from authority. An agent may be allowed to discover that an update tool exists without being allowed to use it for every tenant, environment or record. Build the permitted tool set from the caller’s current scope, then repeat the authorization check inside the handler. This prevents a stale conversation, cached tool list or manipulated description from becoming an accidental permission grant.

A runnable policy gate

The following Python example validates a proposed credit adjustment. It accepts only known fields, applies an amount limit, requires approval for a state-changing request and uses an idempotency key to prevent duplicate execution.

from dataclasses import dataclass

ALLOWED_REASONS = {"billing_error", "service_credit"}
executed = set()

@dataclass(frozen=True)
class Request:
    account_id: str
    amount: int
    reason: str
    idempotency_key: str

def validate(payload):
    expected = {"account_id", "amount", "reason", "idempotency_key"}
    if set(payload) != expected:
        raise ValueError("unknown or missing fields")
    request = Request(**payload)
    if not request.account_id.startswith("acct_"):
        raise ValueError("invalid account identifier")
    if not 1 <= request.amount <= 100:
        raise ValueError("amount outside policy")
    if request.reason not in ALLOWED_REASONS:
        raise ValueError("reason not allowed")
    if len(request.idempotency_key) < 12:
        raise ValueError("weak idempotency key")
    return request

def execute(request, approved=False):
    if not approved:
        return {"status": "approval_required", "preview": request}
    if request.idempotency_key in executed:
        return {"status": "duplicate_ignored"}
    executed.add(request.idempotency_key)
    return {"status": "applied", "account_id": request.account_id}

payload = {
    "account_id": "acct_2048",
    "amount": 25,
    "reason": "service_credit",
    "idempotency_key": "case-2048-v1",
}

request = validate(payload)
print(execute(request))
print(execute(request, approved=True))
print(execute(request, approved=True))

The example deliberately keeps execution synthetic. In a real integration, bind authorization to the authenticated caller, store idempotency keys durably and commit the action in the same transaction that records its result. Do not trust an approved value supplied by the model; derive it from a separate policy or review decision.

Record the decision, not hidden reasoning

An audit event should capture the tool name, normalized arguments or a safe digest, caller identity, policy version, approval decision, idempotency key, execution outcome and correlation identifier. Avoid storing secrets or unnecessary prompt content. The goal is to reconstruct what crossed the boundary and why the application allowed it, not to preserve private model reasoning.

NIST’s Generative AI Profile organizes risk work around governance, mapping, measurement and management. Tool telemetry supports all four: ownership is explicit, affected resources are mapped, failure rates are measurable and controls can be revised from observed evidence.

Test contracts as adversarial interfaces

Unit tests should cover valid calls, missing fields, unknown fields, boundary values, unauthorized resources, duplicate keys, rejected approvals and simulated downstream failures. Add cases in which untrusted retrieved text asks the agent to ignore policy or call a more powerful tool. The model may still propose the call; the contract must deny it.

Evaluate changes with paired cases instead of a single success rate. The approach in LLM evaluation with uncertainty helps separate genuine improvement from sampling noise. For inputs that may contain personal or confidential data, apply data minimization before prompting and again before logging.

A production-ready agent does not receive broad authority because its language is convincing. It receives small, typed capabilities whose effects are checked at runtime. Strict schemas make calls parseable; policy gates make them permissible; approvals make sensitive intent explicit; idempotency makes retries safe; and audit events make the system explainable after the fact.
