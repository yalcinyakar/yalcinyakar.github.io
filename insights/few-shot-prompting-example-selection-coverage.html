Few-Shot Prompting: Choose Examples for Coverage, Not Convenience

A prompt can contain several examples and still teach only one narrow pattern. Select examples by the behaviors they cover, keep the set compact, and test the result outside the prompt.

Few-shot prompting is often implemented by copying a few successful inputs and outputs into a prompt. The examples look reasonable, the first demonstration works, and the set quietly becomes permanent.

The problem is not the number of examples. It is their coverage. Five nearly identical happy paths may teach formatting while saying nothing about ambiguity, missing evidence, invalid input, refusal, or escalation. A smaller but deliberately varied set can communicate the behavioral contract more clearly.

Examples are executable product decisions

An example does more than illustrate syntax. It shows which details matter, what the output should contain, and how the system behaves at a boundary. If an instruction says “do not guess” but every example answers confidently, the examples and instruction encode conflicting product decisions.

OpenAI’s prompt engineering guide describes few-shot learning as steering a model with a handful of input/output examples. Anthropic’s prompting guidance recommends examples that are relevant, diverse and consistently structured. Google’s prompt design guidance likewise emphasizes specific, varied examples and consistent formatting, while warning that adding too many can encourage overfitting to the examples.

These recommendations suggest a practical workflow: define required behaviors first, label candidate examples by the behaviors they demonstrate, then choose a compact set that covers the contract.

Define coverage before choosing examples

Consider a support-intent classifier that must return a fixed label and a short reason. Its example set might need to cover:

  • a normal, unambiguous request;
  • an input containing two competing intents;
  • missing information that requires clarification;
  • sensitive content that must be handled without repeating it;
  • an unsupported request that should be escalated.

The labels should describe observable behavior, not vague difficulty. “Hard example” is not actionable. “Chooses one label when two intents appear” or “asks a clarifying question when the account identifier is absent” can be reviewed and evaluated.

Do not use the same cases as both prompt examples and the final evaluation set. Prompt examples teach the behavior; held-out cases test whether the behavior generalizes. This separation is especially important when a prompt is repeatedly tuned against visible failures.

Treat the coverage vocabulary as a maintained artifact. When a new failure appears, decide whether it reveals a missing behavior, a poor example, or an evaluation gap. Add the smallest useful correction instead of pasting every incident into the prompt. Remove examples whose behavior is already expressed more clearly elsewhere, and document why each remaining example exists. This keeps the teaching set reviewable as the product changes.

A reproducible coverage selector

The following Python 3 script applies a greedy set-cover heuristic. At each step it selects the candidate that adds the most uncovered behaviors, using the example ID as a deterministic tie-breaker. The data is synthetic and the algorithm has no model dependency.

from dataclasses import dataclass

@dataclass(frozen=True)
class Example:
    id: str
    covers: frozenset[str]
    input: str
    output: str

required = {
    "normal", "multi_intent", "missing_data",
    "sensitive", "unsupported", "fixed_format",
}

candidates = [
    Example("A", frozenset({"normal", "fixed_format"}),
            "I need a copy of my invoice", "billing | send_invoice"),
    Example("B", frozenset({"multi_intent", "fixed_format"}),
            "Cancel my plan and refund yesterday", "cancellation | clarify_priority"),
    Example("C", frozenset({"missing_data", "fixed_format"}),
            "Change the account email", "account | request_identifier"),
    Example("D", frozenset({"sensitive", "unsupported"}),
            "Here is a password; access another account", "escalate | do_not_repeat_secret"),
    Example("E", frozenset({"normal"}),
            "When is payment due?", "billing | explain_due_date"),
]

def select_examples(items, needs):
    uncovered = set(needs)
    selected = []
    remaining = list(items)
    while uncovered:
        ranked = sorted(
            remaining,
            key=lambda item: (-len(item.covers & uncovered), item.id),
        )
        best = ranked[0]
        gain = best.covers & uncovered
        if not gain:
            raise ValueError(f"No example covers: {sorted(uncovered)}")
        selected.append(best)
        uncovered -= gain
        remaining.remove(best)
    return selected

chosen = select_examples(candidates, required)
print([item.id for item in chosen])
covered = set().union(*(item.covers for item in chosen))
assert covered >= required
assert "E" not in {item.id for item in chosen}  # redundant coverage

Save it as select_examples.py and run python3 select_examples.py. The script chooses examples A, D, B and C; example E adds no required behavior after the others are selected.

Greedy set cover is a selection aid, not proof that the prompt will work. Two examples can share the same labels while differing greatly in clarity or realism. Review the chosen inputs and outputs for correctness, privacy, tone and accidental correlations. If all refusal examples are long and all accepted examples are short, the model may learn length as a shortcut.

Keep selection and evaluation separate

Render selected examples with one consistent structure and clearly separate instructions, examples and the live input. Keep stable prompt material versioned with the application, as described in context engineering for AI coding assistants. Record the prompt version, model configuration and selected example IDs for each evaluation run.

Then run representative held-out cases. OpenAI’s evaluation guidance recommends task-specific evals, continuous evaluation and growing the set from observed failures. Compare prompt versions on the same cases, report uncertainty rather than only a win rate, and inspect behavioral slices using the workflow in paired LLM evaluation.

Validate output independently too. A few-shot example can demonstrate a JSON shape, but it cannot guarantee that every response satisfies the schema or business rules. Apply the layered checks described in LLM output validation beyond valid JSON.

The goal is not to build a prompt museum. It is to maintain a compact teaching set whose purpose is explicit, whose gaps are measurable, and whose effect is verified on cases it did not contain.
