AI-Generated Tests: Verify the Oracle, Not Just the Coverage

A green test suite is only useful when its expectations are right. Ask AI to propose cases, then prove those cases can detect a meaningful fault.

An AI assistant reads a function, generates ten tests, and reports that everything passes. The result looks productive. Yet the tests may simply reproduce the function's assumptions, including its defects. More executable assertions do not automatically mean stronger evidence.

The missing question is about the test oracle: how does the test know the correct outcome? In AI-assisted QA, that question deserves attention before test count, coverage percentage, or the fluency of the generated explanation.

Separate the requirement from the implementation

Start with an explicit behavioral contract. For a fictional shipping calculator, suppose the subtotal is expressed in integer cents. Subtotals below 5,000 incur a 499-cent fee; subtotals at or above 5,000 ship free. Negative values and non-integers are invalid. These are invented rules for a reproducible exercise, not a description of any commercial system.

Give the assistant that contract and ask it to propose a decision table before writing code. Require a reason for every case. The important examples are zero, one cent below the threshold, the threshold itself, one cent above it, and invalid input.

Review that table independently. If the requirement is ambiguous, preserve the ambiguity as an open design decision rather than letting generated code silently settle it. A model cannot turn an unspecified business policy into an authoritative expectation.

A runnable boundary test with a deliberate fault

This Python 3 script uses only the standard library. Save it as shipping_checks.py. The expected values come directly from the stated contract, not from calling the implementation a second time.

import sys
import unittest

MUTANT = "--mutant" in sys.argv

def shipping_fee(subtotal):
    if type(subtotal) is not int or subtotal < 0:
        raise ValueError("subtotal must be nonnegative integer cents")
    free = subtotal > 5000 if MUTANT else subtotal >= 5000
    return 0 if free else 499

class ShippingContract(unittest.TestCase):
    def test_thresholds(self):
        cases = [(0, 499), (4999, 499), (5000, 0), (5001, 0)]
        for subtotal, expected in cases:
            with self.subTest(subtotal=subtotal):
                self.assertEqual(shipping_fee(subtotal), expected)

    def test_invalid_inputs(self):
        for subtotal in (-1, 50.0, "5000", None, True):
            with self.subTest(subtotal=subtotal):
                with self.assertRaises(ValueError):
                    shipping_fee(subtotal)

if __name__ == "__main__":
    unittest.main(argv=[sys.argv[0]], verbosity=2)

Run python3 shipping_checks.py: both test methods should pass. Then run python3 shipping_checks.py --mutant: the threshold subtest should fail because 5,000 now incorrectly attracts a shipping fee. The second command should return a nonzero exit status.

The official unittest documentation describes the assertions and subtests used here. Subtests keep the individual input visible while checking several cases in one method. Explicitly rejecting booleans avoids Python's otherwise legitimate treatment of bool as an integer subtype.

This is one hand-selected mutation, not a complete mutation-testing framework. Detecting it proves sensitivity to this particular boundary fault; it does not prove the program correct. Removing the 5,000 case demonstrates the limitation: all remaining checks can pass even with the mutant enabled.

Use AI to expand hypotheses, not define truth

A useful prompt asks for missing equivalence classes, boundary conditions, and plausible defects. For example: “Using this contract, propose cases that distinguish greater-than from greater-than-or-equal. Explain each expected result. Do not change the implementation or existing assertions.”

Then inspect what was generated. Reject tests that calculate the expected result using the same branch logic as the implementation. Avoid broad exception catches that make unexpected failures look successful. Review mocks carefully: replacing the behavior being tested with a canned response can leave only the mock under examination.

For larger input spaces, ask for invariants as additional hypotheses. Under this contract, every valid subtotal has a fee of either zero or 499. That invariant is useful but insufficient: an implementation returning zero for every input still satisfies it. Combine properties with explicit examples rather than treating either as universal proof.

Protect the tests as part of the review boundary

Review generated test changes separately from implementation changes. An assistant asked to make a build pass might propose weakening an assertion, skipping a difficult case, or adjusting a fixture to match faulty behavior. Those edits need a requirement-based explanation.

OWASP's Secure Coding with AI guidance recommends human review of AI-generated test modifications and warns against treating passing tests as sufficient security evidence. Apply that principle especially to authorization, validation, and error-handling cases. Use synthetic fixtures, and execute generated tests without production credentials or unrestricted network access.

Make the evidence useful in CI

Commit the reviewed tests and contract together. Run deterministic checks on every relevant change, retain failure output, and keep deliberate-fault experiments in an isolated job or disposable branch. Do not merge the mutant into the shipping implementation.

Record which requirement each regression protects and which plausible fault it detects. Track escaped defects and review effort alongside execution coverage. As discussed in restoring trust in CI tests, a noisy signal becomes easy to ignore. Keep time, randomness, external dependencies, and shared state controlled.

The same separation of evidence and output underpins RAG evaluation and verification in agent harnesses. Generated work is a candidate artifact. Acceptance requires an independent check.

AI can help propose test ideas and draft repetitive scaffolding. The engineering responsibility remains concrete: define the contract, verify the oracle, demonstrate that meaningful faults are caught, and keep the review trail. A smaller suite that detects the wrong behavior is more informative than a larger suite that merely agrees with it.
